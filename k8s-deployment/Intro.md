### 1. 文件用途详解

您可以把 `k8s-deployment` 目录下的所有文件想象成一套完整的“部署说明书和工具箱”。

#### 第一类：Kubernetes 配置文件 (`.yaml` 文件)

这些是核心的“蓝图”文件。您通过它们向 Kubernetes 描述“我想要我的系统长什么样”，Kubernetes 会自动地去实现这个“最终状态”。

-   `00-namespaces.yaml`: **隔离环境的定义**。Namespace（命名空间）就像在物理集群上划分出的“虚拟集群”。我根据您的分组要求，为每个服务组（如 `se2303-core-business`）创建了一个独立的 Namespace，这样不同组的服务就不会互相干扰，管理起来非常清晰。

-   `01-` 到 `03-infrastructure-*.yaml`: **基础设施“蓝图”**。这三个文件分别定义了如何部署 MySQL、Redis 和 Elasticsearch。它们都包含了：
    *   `Deployment`: “部署”的定义，说明了应该使用哪个容器镜像、需要多少个副本、需要哪些环境变量等。
    *   `Service`: “服务”的定义，为后端的多个 Pod（容器实例）提供一个**固定、统一的访问入口和网络地址**。其他服务通过这个 Service 名称就能找到它，无需关心 Pod 的 IP 地址。
    *   `PersistentVolumeClaim (PVC)`: “持久化存储声明”，向 Kubernetes 申请一块硬盘空间来存储数据（如数据库文件），确保即使 Pod 重启，数据也不会丢失。
    *   `Secret`: 用于存储敏感信息，比如数据库密码。

-   `04-configmaps-secrets.yaml`: **全局配置中心**。
    *   `ConfigMap`: 存储**非敏感**的配置信息。我在这里定义了所有微服务的地址（例如 `USER_SERVICE_HOST: user-service.se2303-core-business.svc.cluster.local`），这是实现服务发现的关键。
    *   `Secret`: 存储**敏感**的配置。我把所有服务都需要用到的 JWT 密钥、腾讯云和 JAccount 的密钥都放在这里，并通过 Base64 进行了编码。

-   `05-` 到 `09-*.yaml`: **应用微服务“蓝图”**。这些文件定义了您的每一个微服务（如 `user-service`, `gateway` 等）如何部署。它们同样包含了 `Deployment` 和 `Service` 的定义，并从上面提到的 `ConfigMap` 和 `Secret` 中读取配置。

-   `10-hpa-autoscaling.yaml`: **自动伸缩规则**。`HorizontalPodAutoscaler (HPA)` 是 Kubernetes 的一个强大功能。这个文件定义了“当某个服务（比如网关）的 CPU 使用率超过70%时，自动增加 Pod 数量（最多10个）；当负载下降时，自动减少 Pod 数量（最少2个）”。这完美实现了您对动态扩缩容的需求。

#### 第二类：镜像构建文件

-   `dockerfiles/Dockerfile.template`: **容器镜像的“菜谱”**。Dockerfile 是用来构建 Docker 镜像的脚本。我为您提供了一个通用的模板，它采用了“多阶段构建”技术，先用一个包含完整构建工具（Maven）的镜像来编译您的 Java 代码，然后将编译好的 `.jar` 文件复制到一个非常小巧的纯净 Java 运行环境镜像中。这样做的好处是**最终生成的镜像体积小、更安全**。

-   `build-images.sh`: **自动化构建脚本**。您的项目有这么多微服务，如果手动为每个服务都执行一遍 `docker build` 命令会非常繁琐。这个脚本就是为了解决这个问题，它会自动遍历所有服务，使用上面的 `Dockerfile.template` 为每个服务构建好 Docker 镜像，并打上合适的标签。

#### 第三类：部署与管理脚本

-   `deploy.sh`: **一键部署“总开关”**。这是您最常使用的工具。它封装了所有复杂的 `kubectl` 命令，提供非常简单的接口来管理您的整套系统。
    *   `./deploy.sh deploy`: 一键部署所有服务。
    *   `./deploy.sh deploy-group <group_name>`: 按组部署。
    *   `./deploy.sh cleanup`: 一键删除所有部署的资源，方便测试和清理。
    *   `./deploy.sh status`: 查看当前部署的状态。
    *   `./deploy.sh scale ...`: 手动扩容或缩容某个服务。

### 2. 核心问题解答

#### 问题一：服务发现是如何解决的？

这是一个非常核心的问题。在您本地开发时，服务之间通过 `localhost:端口号` 访问。但在云上，服务的 IP 地址是动态变化的，不能写死。Kubernetes 通过 `Service` 和 `DNS` 完美解决了这个问题：

1.  **创建服务名**: 当我们为 `user-service` 创建一个 `Service` 时，Kubernetes 会自动在内部的 DNS 系统中注册一个域名，格式为：`<服务名>.<命名空间>.svc.cluster.local`。例如，`user-service.se2303-core-business.svc.cluster.local`。这个域名是**固定不变**的。
2.  **注入配置**: 我在 `04-configmaps-secrets.yaml` 文件中，将这些固定的服务域名定义成了环境变量。
3.  **服务访问**: 当网关 (`se2303-gateway`) 需要访问用户服务时，它会读取环境变量 `USER_SERVICE_HOST`，得到那个固定的域名。网关只需要访问这个域名，Kubernetes 的 DNS 系统就会自动将请求解析并负载均衡到 `user-service` 某个健康的 Pod 上。

**总结：我们用 Kubernetes 提供的、稳定的服务域名，替代了过去写死的 `IP:端口`，从而实现了动态的服务发现。**

#### 问题二：`app.cookie.domain` 是如何设置的？

您提到 `user-service` 需要知道网关的域名来正确设置 Cookie。这个问题是这样解决的：

1.  **参数化**: 我在 `06-core-business-services.yaml` 中，将 `user-service` 的 `app.cookie.domain` 配置成了一个从环境变量 `APP_COOKIE_DOMAIN` 中读取的参数。
2.  **部署时注入**: 在 `deploy.sh` 脚本中，有一个步骤是**自动更新**这个域名。当您执行部署时，脚本会把您设置的域名（或者后面会讲到的临时 IP 地址）填入到 `user-service` 的部署配置中。
3.  **动态生效**: 这样，`user-service` 在启动时就会获取到正确的网关域名，而这个域名本身是您在部署时指定的，非常灵活。

### 3. 阿里云ACK实战指南

虽然 ACK 控制台界面可能会更新，但核心步骤和概念是不变的。

**第 1 步：创建 ACK 集群**

1.  登录阿里云控制台，搜索“容器服务 ACK”。
2.  点击“创建集群”。
3.  **选择集群类型**: 选择“**ACK 托管版**”（推荐，帮您管理了底层复杂性）。
4.  **配置集群**:
    *   **地域**: 选择离您用户近的地域。
    *   **VPC**: 如果没有，可以新建一个默认的 VPC。
    *   **节点配置 (Worker 节点)**: 这是运行您应用的服务器。建议至少选择 **3 个节点**以保证高可用。节点规格建议 **4核8GB** 或更高。
5.  点击创建，等待几分钟，集群就会准备就绪。

**第 2 步：连接到您的集群**

1.  在 ACK 集群的管理页面，找到“连接信息”或“基本信息”标签页。
2.  这里会提供一个 **KubeConfig** 配置。复制这个配置。
3.  在您的电脑上（或者一个用作跳板机的云服务器上），安装 `kubectl` 工具。
4.  将复制的 KubeConfig 内容粘贴到您电脑的 `~/.kube/config` 文件中。
5.  **验证连接**: 打开终端，运行 `kubectl get nodes`。如果能看到您刚刚创建的几个节点信息，说明连接成功了！

**第 3 步：创建和使用 ACR 镜像仓库**

您的 Docker 镜像需要一个地方存放，ACK 才能拉取到。阿里云的“容器镜像服务 ACR”就是做这个的。

1.  在阿里云控制台搜索“容器镜像服务 ACR”。
2.  选择“个人版”或“企业版”（个人版免费，足够用）。
3.  **创建命名空间**: 比如创建一个叫 `se2303` 的命名空间。
4.  **创建镜像仓库**: 在 `se2303` 命名空间下，为您的**每一个微服务**都创建一个仓库，例如 `gateway`, `user-service` 等。
5.  **登录和推送**:
    *   在 ACR 的“访问凭证”页面设置一个固定密码。
    *   在您的终端执行登录命令：`docker login --username=<你的阿里云用户名> registry.cn-hangzhou.aliyuncs.com` (地址换成你的)。
    *   **修改镜像标签**: 运行 `./build-images.sh` 后，需要给镜像重新打上 ACR 的标签，例如：
        ```bash
        docker tag se2303/user-service:latest registry.cn-hangzhou.aliyuncs.com/se2303/user-service:latest
        ```
    *   **推送镜像**:
        ```bash
        docker push registry.cn-hangzhou.aliyuncs.com/se2303/user-service:latest
        ```
    *   对所有微服务重复此操作。
6.  **重要：更新 YAML 文件**：将所有 `.yaml` 文件中 `image:` 字段的值，从 `se2303/user-service:latest` 修改为您在 ACR 中的完整镜像地址。

**第 4 步：执行部署**

现在万事俱备！

1.  在您的终端，`cd` 到 `k8s-deployment` 目录。
2.  执行部署命令：`./deploy.sh deploy`。
3.  脚本会自动将所有“蓝图”提交给您的 ACK 集群，ACK 会开始创建所有服务。

**第 5 步：获取访问入口 IP**

1.  在 ACK 控制台，进入您的集群，选择“网络” -> “服务”。
2.  找到一个 `nginx-ingress-controller` 相关（或类似名字）的服务，它的类型是 `LoadBalancer`。
3.  在它的详情里找到“外部端点”或“负载均衡地址”，这就是您整个系统的公网入口 IP！

### 4. 无法购买/备案域名怎么办？

**完全可以！** 这是一个非常常见的情况，特别是对于学习和开发阶段。我们有非常好的替代方案：

**方案一：使用 IP 地址直接访问 (有局限性)**

您可以直接使用上面第 5 步获取到的**公网入口 IP**来访问您的服务。但这里有个问题：
`app.cookie.domain` 不能设置为 IP 地址，这会导致 `user-service` 设置的 JWT 认证 Cookie 无法被浏览器正确保存和发送，**登录功能会失效**。

**方案二：修改本地 `hosts` 文件 (强烈推荐)**

这是一个完美的开发和测试方案，可以让您在没有真实域名的情况下，模拟拥有一个域名的效果。

1.  **获取公网 IP**: 按照上面的方法，拿到 Ingress 的公网入口 IP，例如是 `47.100.100.100`。
2.  **选择一个假域名**: 随便想一个，比如 `se2303.dev`。
3.  **修改 `hosts` 文件**:
    *   **Windows**: `C:\Windows\System32\drivers\etc\hosts` (需要用管理员权限的记事本打开)
    *   **macOS/Linux**: `/etc/hosts` (使用 `sudo nano /etc/hosts` 编辑)
    *   在文件末尾添加一行：
        ```
        47.100.100.100  se2303.dev
        ```
4.  **部署**: 在执行部署脚本时，带上这个假域名：
    ```bash
    DOMAIN=se2303.dev ./deploy.sh deploy
    ```
5.  **访问**: 现在，您可以在**您自己的电脑浏览器**中输入 `http://se2303.dev` 来访问您的服务了！对于您的电脑来说，`se2303.dev` 就是 `47.100.100.100`。`user-service` 设置的 Cookie 域名是 `se2303.dev`，一切都能完美工作！

这个方案的唯一限制是，只有修改了 `hosts` 文件的电脑才能通过域名访问，但这对于开发和演示已经完全足够了。
